# Rules for AI

Guidelines for any AI assistant (e.g. Claude) writing or editing content in this repository.

1. Even though input from the team may be written in a messy, informal, or stream-of-consciousness way, everything written *into* the repository (README files, documentation, notes, etc.) should be as clean and polished as possible.
2. Use bullet lists, numbered lists, tables, etc. when they help organize information (e.g. team member lists, step-by-step protocols, comparisons). Otherwise, use well-structured paragraphs.
3. Keep formatting consistent and symmetric across similar entries (e.g. every team member listed with the same structure: name, role, institution).
4. Keep language scientifical precise, but easy enough to be followed even by BSc students.
5. Everything written must render correctly on GitHub (GitHub-flavored Markdown). Avoid constructs that GitHub doesn't render as intended — e.g. Markdown syntax (like `**bold**`) nested inside raw HTML blocks, which GitHub displays as literal characters instead of formatting. When centering or otherwise styling text requires HTML, use HTML tags for the emphasis too (e.g. `<strong>`, `<em>`) instead of mixing in Markdown syntax.
6. In R chunks, don't let a computed quantity (a count, volume, total, etc.) print as bare/standalone chunk output. Weave it into the surrounding sentence instead, via inline code (e.g. "we need `` `r Phytoplankton_vessels_total` `` vessels"), so every number a reader sees is anchored in a sentence explaining what it means. Concretely, this means no line in an R chunk should just be a variable name or other unassigned expression on its own (e.g. `Weight_per_shelf_kg` sitting by itself after computing it) — knitr auto-prints that, regardless of code-fold settings, wherever it sits in the chunk, not just on the last line. Every line should be an assignment, a control-flow statement, or output that's genuinely meant to render (e.g. a `cat(..., results='asis')` chunk building markdown). After adding or editing any chunk, actually check the rendered output for a stray value/`[1] ...` block near it, don't just eyeball the source for correctness.
7. Use consistent, established terminology for recurring objects across prose, diagrams, and parameter names, rather than switching between generic descriptions of them (e.g. "the small bottle") and their real names. In the phytoplankton growth procedure: the 50 mL vessel is the **stock flask**, the 500 mL vessel is the **stock bottle**, and the 2000 mL vessel is the **experimental bottle**.
8. R code chunks (calculations, parameter definitions, etc.) should stay collapsed by default in the rendered HTML, not shown inline — this is what `format.html.code-fold: true` and `code-summary: "Show calculation code"` in [1_master.qmd](1_experiment/1_master.qmd)'s YAML header do; keep that setting in place, and don't add `#| echo: false`/`#| code-fold: false` overrides to individual chunks unless a chunk should never show its code at all (e.g. one whose only job is emitting a diagram or other generated markdown).
9. When writing a protocol, keep each footnote immediately after the protocol it belongs to, not collected at the end of the document after multiple protocols. If several protocols each have footnotes, each protocol keeps its own footnote block.
10. Follow Robert C. Martin's *Clean Code* philosophy on comments in any code (R chunks, scripts, etc.): the code itself — clear variable/function names, small well-scoped pieces — should do the explaining wherever possible; a comment is a fallback for what code can't express, not a substitute for writing it clearly. Only add a comment when it carries information the code itself cannot: the *why* behind a non-obvious choice (e.g. the source of a number), a warning of a consequence, or a genuine TODO. Never add a comment that just restates what the line already says, and remove a comment if the code around it changes and the comment no longer holds true.
11. Every time you push to the GitHub repository, update [`CHANGELOG.md`](CHANGELOG.md) (repo root, kept out of the rendered Quarto document) with what changed since the last entry. Follow [Keep a Changelog](https://keepachangelog.com/) conventions, adapted for a project without version numbers: newest entry first, dated, changes grouped under headings like `Added`/`Changed`/`Fixed`/`Removed` when that helps. Each bullet should be a short, plain-English sentence describing what changed and why it matters — written for the user reading it months later to quickly understand what happened, not a restatement of the diff or commit log.
